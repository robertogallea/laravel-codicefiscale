# Localized, per-failure validation messages are restored, scoped entirely to the Laravel layer

3.x's initial cut dropped 2.x's translated validation messages entirely, leaving both `CodiceFiscaleRule` and the `codice_fiscale` string-rule alias hardcoding one generic English sentence regardless of which of `ValidationError`'s 5 cases actually fired. This restores 2.x's `lang/en/validation.php` / `lang/it/validation.php` file layout, `codicefiscale` translation namespace, and `lang` publish tag - registered via `loadTranslationsFrom()`/`publishes()` in `CodiceFiscaleServiceProvider::boot()` - with one key per `ValidationError` case plus a `mismatch` template for `->matching()`. Core's `ValidationError` (`src/Enums/ValidationError.php`) gains no `message()`/`label()` method and stays a bare backed string enum: message text is a presentation concern, and ADR-0002/ADR-0004's framework-agnostic Core boundary already draws that line - a message-free Core lets a non-Laravel consumer use `Validator`/`Matcher` without inheriting an opinionated, English-language dependency it never asked for.

Both failure-producing call sites now use `ValidationResult->errors(): list<ValidationError>` and `MatchResult->mismatched(): list<PersonField>` - previously computed but discarded in favor of a boolean - to emit one translated message per distinct failure reason. `CodiceFiscaleRule::validate()` calls Laravel's `$fail()` once per `ValidationError` (and once per mismatched `PersonField`), which the `ValidationRule` contract already supports natively - no new plumbing. The `codice_fiscale` string alias, registered via `ValidationFactory::extend()`, can't do the same: `extend()`'s single boolean callback and static message parameter can't vary per failure reason on their own. 2.x solved this identical problem with a per-instance `Validator::addReplacer()` call inside the extension callback; this restores that same mechanism at the Factory level instead, via `ValidationFactory::replacer()` - registered once at boot rather than once per validation run, and recomputing the attribute's `ValidationError` list from `$validator->getData()[$attribute]` rather than closing over state from the `extend()` callback, so it holds correctly if the same rule string validates multiple attributes in one request. The replaced message concatenates one translated fragment per error (space-joined) into the single message slot `extend()`'s message bag allows, rather than the class-based rule's multiple independent `$fail()` calls - the two paths converge to the same translated text per failure reason whenever exactly one error fires, which is what the test suite checks call-site parity against.

`->matching()`'s mismatch message uses one `mismatch` template, not one key per `PersonField`: the caller already names their own request field per `Matcher` field (`firstName: 'first_name'`), so the message interpolates that caller-chosen name via `:field` rather than a translated per-field label - the request's own naming is the consuming app's concern, not this package's. This also caps mismatch granularity below 2.x's finer `wrong_birth_day`/`wrong_birth_month`/`wrong_birth_year` split, since `PersonField::BirthDate` is a single case; splitting it back apart is a `Matcher`/`PersonField` redesign, out of scope here.

**Consequences**: an app that published `lang/vendor/codicefiscale/it/validation.php` under 2.x keeps the same structural publish-and-override workflow, though the key set changed shape and old customizations don't carry over content-wise. Default-locale (English) behavior is additive, not breaking - callers who never localized see specific rather than generic text, but validation pass/fail outcomes are unchanged.
