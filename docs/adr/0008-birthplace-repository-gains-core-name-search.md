# BirthPlaceRepository gains a Core `search()` method, backed by a precomputed normalized name column

Name-based lookup ("what's the code for 'Roma'?") is a genuine domain capability, not a storage-specific one, so `search(string $name, ?DateTimeImmutable $on = null, ?int $limit = null): array` joins the Core `BirthPlaceRepository` interface alongside `find()`/`existedEver()` — unlike ADR-0004's Eloquent range queries, which stayed Laravel-only because the *mechanism* (not the concept) was storage-specific. Matching is case/accent-insensitive substring against a precomputed `name_normalized` column, populated by the importers and indexed, rather than normalized at query time in PHP; results are one row per matching era-record (unfiltered by `on` unless given, so a renamed comune's old names still surface), ordered most-recent-era-first when `limit` truncates. `CompositeBirthPlaceRepository::search()` queries both the domestic and foreign tables and merges, since a name carries no code to route on the way `find()` does.

**Considered options**: normalizing at query time instead of a stored column — rejected, since it can't use an index and forces every search to pull its candidate set into PHP for ~20k historical rows. Keeping `search()` Laravel-layer-only, mirroring ADR-0004 — rejected, since name search is a capability any `BirthPlaceRepository` implementation should be expected to support, not an artifact of Eloquent's query builder.

**Consequences**: `Person`/`Generator` stay `BirthPlaceCode`-only. `search()` surfaces candidates for a caller to disambiguate, but generation never auto-resolves a bare name itself — a name resolving to exactly one match today isn't a stable property as more historical data loads, and silent auto-resolution would reintroduce the kind of implicit behavior ADR-0001's clean break moved away from. The `name_normalized` column needs no separate backfill step: the importers already `upsert()` keyed on `(code, valid_from)`, so adding the column to their `toRecord()`/`update` mapping means the next `codice-fiscale:update-places` run backfills existing rows automatically.
