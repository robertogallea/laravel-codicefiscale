# Laravel Boost guideline + skills ship with the package, pointing at README/UPGRADE instead of duplicating them

An AI agent working in an app that depends on this package has no first-class signal that it exists or what its 3.x API looks like, and no structured path to correct 2.x→3.x migration guidance. `resources/boost/guidelines/core.blade.php` (always loaded, minimal) introduces the package and directs the agent to activate one of two `resources/boost/skills/{slug}/SKILL.md` (loaded on demand, following the external Agent Skills format): `using-laravel-codicefiscale` for everyday 3.x usage, `upgrading-laravel-codicefiscale-from-v2` for migration. Both skill bodies are condensed and task-oriented, pointing at this package's own `README.md`/`UPGRADE.md` for the exhaustive method-by-method detail rather than duplicating it, so the skills can't drift out of sync with the docs that are already the source of truth. Skill slugs are package-scoped (`using-laravel-codicefiscale`, not `using`) to stay unambiguous next to other installed packages' similarly-named skills, following the precedent set by `prism-php`'s own `developing-with-prism` skill. These files describe the unreleased 3.x API - consistent with `README.md`/`UPGRADE.md` already doing the same on this line of work - so they only take effect for consumers once a 3.x release actually ships; nothing here works against the current 2.3.1 line.

**Considered options**: duplicating the relevant README/UPGRADE content directly into the skills for a fully self-contained agent experience - rejected, since it creates two places to update every time the API changes, with no enforcement that they stay in sync. Shipping skills only, no guideline - rejected, since without a guideline there's no always-loaded signal that the skills exist at all; the guideline+skills split mirrors the real-world pattern Boost's own third-party examples use. Generic skill slugs (`using`, `upgrading-from-v2`) - rejected in favor of package-scoped slugs, since Boost surfaces skill names without a package namespace prefix, so a generic slug could collide with another installed package's identically-named skill.

**Consequences**: Regression coverage (`tests/Feature/BoostSkillsTest.php`) exercises Boost's real discovery/parsing classes (`ThirdPartyPackage::discover()`, `SkillComposer::skills()`) rather than reimplementing that logic, but Testbench's skeleton app has no `vendor/` directory of its own - Boost's discovery reads `base_path('vendor')`/`base_path('composer.json')` directly, since it doesn't care about PHP autoloading. The test fakes a minimal "consuming app" view of this package (a symlink plus a temporary `composer.json` `require` entry) inside the skeleton for the duration of each test, rather than adding a permanent, committed Testbench workbench app - this keeps the fake scoped to exactly what Boost's discovery needs, with nothing left behind between test runs. `laravel/boost` is a permanent `require-dev` dependency as a result, even though the package itself has no runtime dependency on it. Boost's `BoostServiceProvider::shouldRun()` deliberately no-ops (skipping command registration, MCP, and its browser-log middleware) whenever `app()->runningUnitTests()` is true, so `artisan('boost:install')`/`artisan('boost:list-skills')` can never be exercised through Testbench - the test resolves `SkillComposer`/`ThirdPartyPackage` directly instead, which is Boost's own discovery layer, just reached beneath the command.
